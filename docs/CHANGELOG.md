  **`conditions`-persistence design — approved this session, Option A, with two explicit scope deferrals:**

  - **Decision: a new `trades.conditions jsonb` column (Option A), not a join against `bot_decision_log.details` (Option B).** `bot_decision_log`'s `trade_approved` entry already logs very similar data for the same trade-open moment, which made Option B tempting, but it was rejected for two concrete reasons: (a) there is no FK either direction between `trades` and `bot_decision_log` today — linking them would mean matching on timestamp-proximity + `bot_instance_id`, which is fragile in principle even if fine in practice right now; (b) `bot_decision_log` is an **audit trail** with its own 6-month-then-archive-to-compressed-JSON retention policy (`05_Database_Design.md`), while the Learning Engine's rolling window is a **live, hot-path read on every `BotRuntime.initialize()`** — coupling a statistical input's read path to an audit log's archival lifecycle conflates two concerns that happen to overlap today but shouldn't be structurally tied together. A trade's own defining facts (its `conditions`, same category as `direction`/`entry_price`/`symbol`) belong on the trade's own row, same reasoning as `trades.symbol` in 6.4.
  - **Migration needed: `database/migrations/006_add_trades_conditions.sql`** — `ALTER TABLE trades ADD COLUMN conditions jsonb` — **nullable, no backfill.** Unlike `trades.symbol` in 6.4 (honestly backfillable to `'EURUSD'`, the only symbol ever traded pre-6.4), there is no honest value to backfill existing closed trades' `conditions` to — their real `tradeInput`/`selection` at open time was never captured, so fabricating one would be worse than `NULL`. `loadTradeHistoryForLearning`'s two actual consumers (`computeLiveWinProbability`/`computeConsecutiveLosses`) never read `conditions` at all today, so `NULL` on old rows is functionally harmless, not a gap that needs special-casing.
